# Working on remax

remax is a Haskell terminal review tool built on brick. This file is for
anyone, human or agent, changing the code. The user-facing description
is in README.md.

## Building

- `./scripts/build` is the gate: it formats every source file with
  fourmolu and builds with stack inside the dev container under
  `-Wall -Werror`. Nothing lands without it passing.
- `cabal build exe:remax` is the binary people actually run; their
  `remax` on PATH symlinks into `dist-newstyle`. Build both ways. The two
  paths resolve different dependency versions, so an API that compiles
  under one can fail under the other.
- `remax.cabal` is generated by hpack from `package.yaml`. Modules are
  discovered automatically; the container build regenerates the file.
- There is no test suite. Verify behaviour by driving the real binary
  over a pty with the XDG directories pointed at a scratch location, the
  way `scripts/lib/hero_cast.py` does. Never run it against a store you
  did not create, and only ever kill a process you started yourself.

## Module layout

`Remax.UI` only starts a session. Everything else lives under
`Remax.UI.*` in four trees, listed here in dependency order. A module
imports only modules that appear before it in this list, whether in an
earlier tree or earlier in its own. Haskell already refuses an import
cycle; this is the stronger rule that an import never reaches upward
even when it would compile, so the trees keep meaning something.
`henforcer.toml` makes the tree part of that rule a compile error under
the `ci` flag, and encapsulates `Remax.UI` so nothing outside the session
imports its internals. The order within a tree is convention.

1. `Core` — `Types` (`St`, `FileView`, `REvent`, every type an `St`
   field mentions, and the trivial accessors), `Attrs`, `Markdown`
   (comment bodies as styled rows), `Anchor` (which row a conversation
   draws under), `Threads` (a conversation as rows), `Widgets`, `Jobs`
   (background work), `Verdict` (pending predicates and the per-file
   remark, pending and thread caches), `Ink` (image painting),
   `WordDiff`, `View` (window geometry, note lines), `PullView` (the
   pull request's timeline as rows).
2. `Model` — `Tray`, `Nav` (parking, scrolling, selection), `Watch`
   (filesystem watching), `Work` (your pending work, the conversations
   drawn from it and the poll, and where outdated ones draw), `Load`
   (loading, rebuilding, refresh, reload, highlighting).
3. `Action` — `Threads` (the band, the work popups and the GitHub
   writes), `Cite`, `Conversation`, `Verdicts`, `Tour` (the tour's stops popup), `Rebase`, `Notes`, `Settings`,
   `Submit` (the :submit dialog, after `Open`), `PullView` (the PR view,
   after `Open`),
   `Pull`, `Fuzzy`, `Repo`, `Open`, `Worktree` (edit mode's checkout and
   the moves in and out of it), `Picker`, `Search`, `Uses` (the hunks mentioning a
   name), `Tree`, `Files`,
   `TreeKeys`, `Editor`, `Command`, `Menus`.
4. `Draw` — one module per surface, composed by `Remax.UI.Draw`.
5. `Events` — key and event dispatch, the top of the session.

Placement rules:

- New code goes in the earliest module that can hold it. A function two
  modules need sits before both of them, in a shared module if none
  fits.
- Data that both the drawing and the key handling consult, such as menu
  entries, lives in an action module (`Menus`), never in `Draw.*`.
- Drawing modules read state and produce widgets. They do not perform
  actions or reach into the store.
- Every module has an explicit export list naming only what other
  modules use. Data types are exported with `(..)`. Everything else is
  private.
- Imports follow the rules under Imports below; sibling `Remax.UI.*`
  modules are no exception.
- `Remax.Git`, `Remax.Store`, `Remax.Conversation`, `Remax.WorkStore`,
  `Remax.Submit`, `Remax.RemoteCache`, `Remax.Feedback`, `Remax.Json`,
  `Remax.DiffModel`, `Remax.Modal` and the
  other `Remax.*` modules are below all of `Remax.UI.*` and know nothing
  about the session state.

## Imports

Import every module qualified, in the postpositive form the
`ImportQualifiedPost` default extension allows:
`import Data.Text qualified as T`. Only `Prelude` may be imported open,
apart from the `import M as Export` imports that a module re-exports
with `module Export`. Import operators explicitly and unqualified, e.g.
`import System.FilePath ((</>))` next to
`import System.FilePath qualified as FilePath`. Import operator data
constructors with `pattern`, e.g.
`import Data.List.NonEmpty (pattern (:|))`, which needs the
`PatternSynonyms` extension.

When a module that is already imported re-exports a name, use it through
that module instead of importing the defining module too.

Give each module a single alias and use it everywhere the module is
imported. `henforcer.toml` records every alias and the gate rejects any
other spelling, so add a rule when you import a module that has none,
and add an `unqualified` scheme there when you import a module's
operators. Pick an alias that a reader cannot mistake for a different
module, e.g. `TS` for `Remax.TreeSitter` rather than `Tree`, which reads
as `Remax.Tree`, and `TreeAction` for `Remax.UI.Action.Tree`.

Ensure that each import alias used with a module refers to only one
imported module. Do not use the same import alias for different modules.

## Functions

- A function fits on one screen, about sixty lines. A long case
  dispatch is fine when every branch is a single call to a named
  function; the branches are what get their own functions.
- Lower cyclomatic complexity by splitting on the natural seams: compute
  a plan, do the IO, apply the result. Each of those is its own function.
- Pass named records between steps rather than tuples, as `Refresh`,
  `ReloadPlan` and `RowPaint` do.
- Prefer `let` over `where`, explicit `case x of` over `LambdaCase`,
  and qualified imports for everything but operators.
- Avoid boolean arguments and fields that carry meaning. `WatchMode`
  replaced a `Bool`; follow that pattern with a small sum type.
- Record fields are prefixed with their type (`fvPath`, `stFiles`,
  `rlPath`).

## Concurrency

Anything that can take longer than a frame runs through `startJob` in
`Jobs`: loading, refreshing, reloading, switching repository, describing
repositories for the picker, highlighting large files, recounting.

A job's finish runs on the event loop later and must:

- re-read the state with `get` rather than use what the job captured;
- drop itself when `stEpoch` moved, which a repository switch bumps;
- re-validate before applying, for a file that means the buffer text and
  base are unchanged, and merge the live editor state back in or mark the
  view stale so Esc rebuilds it;
- receive `Either Text a` and clear its own in-flight flag on both
  sides, so a failed job can never leave `stRefreshing`, `stReloading`
  or `stHighlighting` stuck.

Reload and highlight work share the two-slot `stWorkSlots` semaphore.

## Per-frame cost

The draw functions run on every event, including the 120 ms pulse while a
job runs and the 1.5 s presence beat. Nothing in `Draw.*` may walk every
file's rows or index into `stFiles` by position per hunk; on a change set
of twenty thousand files that is a wedge, and `:q` is the only way out.
Per-file facts the frame needs are cached on `FileView` (`fvRemarks`,
`fvPending`) and refreshed by `recountIfChanged` after any event that
changes verdicts or threads.

## Filesystem watching

An inotify watch is on a directory's inode. The watch set in `Watch`
forgets a path when its watch dies and re-watches directories that
reappear; a second watch on the same inode doubles every event, so never
watch unconditionally. When inotify is unavailable the session polls:
only `.git` directories and the file on screen are followed, never one
poll thread per directory.

## Comments and commits

- Do not add comments. Leave existing ones in place and correct any that
  a change makes untrue.
- Keep commit messages brief and written for someone reviewing a pull
  request, without references to context they would not have.
- Work happens directly on `main`. Commit there rather than on a feature
  branch, and do not open pull requests. Work done on a branch anyway is
  fast-forwarded onto `main`, never merged with a merge commit.
- Commit titles carry no Shortcut story prefix; remax is not tracked in
  stories.
